## 1. Executive Summary

GPG-Meister is a PyQt-based GPG secret-management tool with a notably security-conscious architecture: mlock-pinned `SecureBytes` buffers, argon2id KDF, AEAD-protected vault format with AAD-bound headers, binary integrity pinning (device/inode + SHA-256), a hash-chained audit log, an allow-listed GPG-binary detector, and defense-in-depth file-permission checks. The adversarial verification process confirmed the core cryptographic and storage design is sound, and rejected four plausible-but-unreachable attack claims (config-trust ordering, fingerprint injection, version-parse crash, trust-pin TOCTOU), reflecting a codebase that fails closed in most paths.

The dominant headline risk is **a security regression caused by branch divergence**: commit `67c6be9` ("fix(security): isolate GPG env, dedicated status-fd, harden legacy vault") is **not an ancestor of the audited HEAD `94e85cd`**. As a result, three advertised hardening measures — GPG subprocess environment isolation, a dedicated status-fd pipe, and NUL-byte passphrase rejection — are absent from the code on disk even though docstrings/commit history imply they exist. The single most valuable remediation is to **cherry-pick / merge `67c6be9` into the release branch**, which closes several findings at once.

After that, the substantive remaining issues are: a **signature-validity gap** that accepts signatures from revoked/expired keys, an **unauthenticated audit hash-chain tip** that defeats tamper-evidence against a same-uid actor, a **clipboard auto-clear that is lost on quit**, a **legacy-vault deserialization path** that bypasses the hardened code, and a **silently-failing in-place memory-wipe routine** that can corrupt interned bytes. No Critical-severity, remotely-exploitable vulnerabilities were found; most issues require local memory access or a pre-existing privileged position, consistent with a desktop secrets tool's threat model.

Tooling hygiene is weak relative to the security posture: `ruff` (19 errors) and `mypy --strict` (51 errors, 7 in `src`) are both advertised as checks but are not green or CI-gated, and SBOM generation is disconnected from the build.

## 2. Vulnerabilities

> Severities below use the adjudicated `adjustedSeverity`. No Critical or High items survived verification. Overlapping env-isolation and status-fd findings (reported from both the `gpg-subprocess` and `deps-packaging-quality` angles) are deduplicated here.

### Medium

#### M1. Signatures from revoked/expired keys are reported as valid
- **File:** `src/gpg_meister/services/gpg_service.py:575-582, 639-651`
- **What & attack scenario:** `decrypt()` sets `valid=True` on the first `VALIDSIG` status record and `verify()` derives validity solely from `proc.returncode == 0`. Neither inspects `GOODSIG`, `EXPKEYSIG` (good sig from an expired key), `REVKEYSIG` (good sig from a revoked key), `EXPSIG`, `ERRSIG`, or `TRUST_*`. GnuPG emits `VALIDSIG` *together with* `REVKEYSIG`/`EXPKEYSIG` and still returns exit code 0 (warning, not error). A message signed by a revoked or expired signing key is therefore surfaced end-to-end (`message_service.py:111/188` → `verify_view.py:104-121` / `decrypt_view.py:141-156`) as "Signature VALID" with attribution — defeating revocation. `signer_trust` comes from web-of-trust/ownertrust and does **not** reflect revocation, so it does not mitigate. (Note: `BADSIG`/`ERRSIG` already cause nonzero exit and are correctly rejected; the gap is specifically the revoked/expired case.)
- **Fix:** Compute validity from status records, not returncode: require `GOODSIG` + `VALIDSIG`; explicitly down-rank/flag `EXPKEYSIG`, `REVKEYSIG`, `EXPSIG`. Bind the returned signer fingerprint to the matching `VALIDSIG` only, and surface expiry/revocation state to the caller.

#### M2. Audit hash-chain tamper detection is fully defeatable (unauthenticated tip)
- **File:** `src/gpg_meister/storage/audit_log.py:144-145, 211-214, 292-302`
- **What & attack scenario:** The chain is keyless plain SHA-256, and the only anti-truncation guard is a sibling `.tip` file holding the last record's hash, with no secret/MAC. A same-uid attacker (the exact threat the chain exists for) can truncate or rewrite `audit.log`, recompute the SHA-256 of the new last line, overwrite `audit.log.tip`, and `verify_chain` returns OK. The docstring overstates this as general tamper detection, giving a false sense of tamper-evidence.
- **Fix:** Either honestly document it as accidental-corruption detection only, or make it keyed (HMAC each record under a key sealed in the OS keyring / a root-owned location), and at minimum embed a monotonic record counter so silent truncation is detectable without the tip file. (Related: `verify-chain-nofollow` below.)

#### M3. Clipboard auto-clear timers are lost on quit, leaving secrets on the clipboard
- **File:** `src/gpg_meister/ui/clipboard.py:40-63`
- **What & attack scenario:** `copy_text` schedules a single-shot `QTimer` (default 60s, configurable) held in module-global `_ACTIVE_TIMERS` to clear the clipboard. If the app quits or crashes before the timer fires, the Qt event loop stops, `_clear` never runs, and the copied secret (decrypted plaintext via `decrypt_view._copy_output`, vault/key material) remains on the system clipboard indefinitely — readable by any app or clipboard-history manager. There is no `aboutToQuit`/`closeEvent` flush anywhere (`app.py` has no quit hook), and `ClipboardButton.stop_timer()` is never wired to a close event. The KDE/NSPasteboard "no-history" MIME hints are best-effort and widely ignored.
- **Fix:** Connect `QApplication.aboutToQuit` to a handler that iterates `_ACTIVE_TIMERS` and clears the clipboard immediately if its current text matches a tracked snapshot. Wire `ClipboardButton.stop_timer()` into widget destroy/close.

#### M4. `_zero_bytes_object` silently fails and can corrupt interned bytes
- **File:** `src/gpg_meister/security/secure_bytes.py:160-173`
- **What & attack scenario:** The load-bearing wipe routine memsets a `PyBytesObject` data buffer at a computed offset with **no length, refcount, or interning guard**, wrapped in `except Exception: pass`. (1) *Correctness:* zeroing a single-byte interned bytes object (demonstrated on the project's CPython 3.12) corrupts interpreter-wide state so every later `b'a'` returns `b'\x00'`. This is reachable: GPG-key passphrase callers (`sign_viewmodel.py:86`, `decrypt_viewmodel.py:57`, `encrypt_viewmodel.py:90`, `key_create_viewmodel.py:112`) call `_zero_bytes_object(normalise_passphrase(pp).encode())` with no minimum-length enforcement, so a single-character GPG passphrase triggers it. (2) *Security:* on any runtime where the offset assumption is wrong (PyPy/future CPython), the secret is silently not wiped, with zero signal — failing open for the argon2 derived-key intermediate (`kdf.py:111`) and passphrase copy (`kdf.py:103`).
- **Fix:** Guard with `len(raw) > 1`, document the invariant, prefer keeping secrets in `SecureBytes`/`bytearray`, and surface wipe failures via a structured log/metric (without the secret) instead of a bare `pass`.

### Low

#### L1. GPG subprocess inherits the full parent environment (no `env=` allow-list)
*(Deduplicated: `no-env-isolation` + `gpg-env-not-isolated`.)*
- **File:** `src/gpg_meister/services/gpg_service.py:287-293` (`_run_gpg`), `658-664` (`version()`)
- **What & attack scenario:** Both subprocess calls pass no `env=`, so `gpg` inherits the entire parent `os.environ`. A process that controls the app's environment (malicious `.desktop` launcher, poisoned shell profile, malicious parent) can set `LD_PRELOAD`/`LD_LIBRARY_PATH`/`DYLD_INSERT_LIBRARIES` to inject code into the `gpg` child at load time — bypassing the binary inode/hash pinning, which validates the file but not the dynamic linker. `--homedir` mitigates `GNUPGHOME`, but `GPG_AGENT_INFO`/`PINENTRY_USER_DATA` are not sanitized. Severity is bounded by the precondition that the attacker already controls the parent environment. **The fix already exists verbatim in commit `67c6be9` (`_clean_env()`), which is not yet on the release branch.**
- **Fix:** Cherry-pick `67c6be9`, or build an allow-list env (`PATH`, `HOME`, `USER`, `LANG`/`LC_*`, `TZ`, `TMPDIR`) and pass it to both calls, explicitly dropping `LD_PRELOAD`/`LD_LIBRARY_PATH`/`DYLD_*`/`GPG_AGENT_INFO`/`PINENTRY_USER_DATA`. Add a unit test asserting `Popen` is called with a sanitized env.

#### L2. `--status-fd` multiplexed onto stderr instead of a dedicated pipe
*(Deduplicated: the two `status-fd-on-stderr` findings.)*
- **File:** `src/gpg_meister/services/gpg_service.py:270-271, 577-582, 639-651`
- **What & attack scenario:** `cmd.extend(["--status-fd", "2"])` puts machine-readable `[GNUPG:]` status on the same stream as human diagnostics, and `_parse_status` scans stderr for them. This is the stream-separation regression the project itself previously fixed (`67c6be9`). The claimed signature-spoofing impact is **not substantiated** — GnuPG reserves the `[GNUPG:] ` prefix for status output and `valid` is derived from returncode, not parsed status — so this is defense-in-depth hardening, not an exploitable bypass.
- **Fix:** Allocate `os.pipe()`, pass the write end via `--status-fd <n>` + `pass_fds`, drain it in a thread, and parse `[GNUPG:]` records only from that buffer. Keep stderr for diagnostics. (Restored by `67c6be9`.)

#### L3. Legacy "all-in-manifest" vault path bypasses hardened deserialization
*(Deduplicated: `legacy-unbounded-msgpack` + `legacy-plaintext-key-heap-leak`.)*
- **File:** `src/gpg_meister/services/vault_service.py:266-301`
- **What & attack scenario:** The legacy branch calls `msgpack.unpack(stream, raw=False)` with **none** of the `max_str_len`/`max_bin_len`/`max_array_len`/`max_map_len` caps that the hardened `_deserialise_manifest` (196-210) applies, and adds no `isinstance` guards before `.get`/`.pop`. (a) *Memory:* a victim opening a tampered-but-validly-encrypted portable vault can amplify allocation — but the impact is bounded by the existing 256 MiB ciphertext cap (`vault_format.py:39`), so it is not the unbounded OOM the original finding implied. (b) *Secret hygiene:* the branch materializes private-key armor into immutable Python `str`/`bytes` (`manifest_obj`, popped strings, `collected_material`, `priv`) that are never zeroed, widening the plaintext-secret window the segmented path (308-347) carefully avoids by slicing from a single wipeable `bytearray`.
- **Fix:** Route legacy bytes through the bounded unpacker (same limits), assert `isinstance(manifest_obj, dict)` / `isinstance(key_entry, dict)`, locate armored byte ranges within the decrypted `bytearray` instead of parsing to `str`, best-effort `_zero_bytes_object` every intermediate, and drop `manifest_obj` before returning. Warn users to re-save in the segmented format.

#### L4. Passphrase copied into an unpinned immutable `bytes` object during KDF
- **File:** `src/gpg_meister/security/kdf.py:85-106`
- **What & attack scenario:** `derive_key` creates `_secret = bytes(passphrase_buf)` (handed to argon2) to dodge a *hypothetical* argon2-cffi bytearray rejection. The bytearray is reliably memset, but `_secret` is only wiped best-effort via the fragile `_zero_bytes_object` offset hack, and the CFFI marshalling copy is unreachable for wiping. A transient plaintext passphrase copy can persist in swappable/dumpable heap.
- **Fix:** Pass the bytearray directly to `hash_secret_raw`; fall back to a bytes copy only on a real `Argon2Error`/`TypeError`, and if unavoidable, use an mlock-pinned buffer. Do not rely on the offset hack as the primary wipe; log (without the value) on wipe-path failure.

#### L5. Passphrase NUL byte not rejected (C-string truncation risk)
- **File:** `src/gpg_meister/services/gpg_service.py:278-279, 398-399`
- **What & attack scenario:** Only `0x0A`/`0x0D` are rejected. A NUL byte in a passphrase passes through `--passphrase-fd`; GnuPG/C-string handlers may truncate at it, so the effective protecting passphrase silently differs from user input. Input-validation robustness gap; `67c6be9` already adds the NUL check in `_run_gpg` (but not `generate_key`).
- **Fix:** Reject `0x00` alongside `0x0A`/`0x0D` in both `_run_gpg` and `generate_key`.

#### L6. Raw `str(exc)` echoed into UI error labels
- **File:** `src/gpg_meister/ui/errors/error_catalog.py:155-173`
- **What & attack scenario:** Only four exception types map to catalog messages; `ValueError` and the generic fallback return `str(exc)` verbatim into a `QLabel` (`decrypt_view.py:161-163`, etc.). Unmapped `GPGProcessError`/`GPGPassphraseError` embed `proc.stderr[:200]`. Verification confirmed this leaks **non-secret diagnostic context** (file paths, key IDs, user IDs, locale-dependent gpg messages) — **not** passphrases or plaintext (those never reach stderr), and the label is not selectable by default. An error-hygiene/information-disclosure weakness, not key-material exposure.
- **Fix:** Map all known exception types; for the unknown fallback show a fixed generic message + correlation id and write detail only to a scrubbed diagnostic log. Treat `ValueError` the same way.

#### L7. Passphrases linger in unzeroed QString / Python `str` memory
*(Deduplicated: `qlineedit-no-zero` + `encrypt-vm-plain-str`.)*
- **File:** `src/gpg_meister/ui/widgets/passphrase_field.py:50-54, 122-126`; `src/gpg_meister/ui/messages/encrypt_viewmodel.py:44, 66-67, 79-93`; `src/gpg_meister/ui/vault/vault_export_viewmodel.py:48-53`
- **What & attack scenario:** Keystrokes land in a `QLineEdit` whose QString buffer is never wiped on `clear()`, and `EncryptViewModel`/`VaultExportViewModel` mirror the passphrase into long-lived plain `str` fields (updated per keystroke) that are only reset on `submit()`. Abandoning the form, switching tabs, or a pre-submit exception leaves plaintext on the Python heap until GC. `DecryptViewModel`'s one-shot `get_passphrase` callable is the correct pattern. Defense-in-depth residue (requires local memory-scrape/core-dump/swap); QString cannot be fully zeroed in Qt.
- **Fix:** Mirror the `DecryptViewModel` callable pattern (read once at submit, never store); clear persisted per-key state in a `clear()`/`closeEvent` path; document the QString limitation in `SecureBytes`' limitations list.

#### L8. Decrypted plaintext lingers in the output widget with no auto-clear
- **File:** `src/gpg_meister/ui/messages/decrypt_view.py:84-97, 128-136, 165-171`
- **What & attack scenario:** After decrypt, cleartext stays in the read-only `QTextEdit` until manual Clear — no idle timer, no clear-on-tab-switch/blur/close. Shoulder-surfing/screen-capture exposure plus session-long heap residency, copyable via the default context menu.
- **Fix:** Auto-clear on the configured clipboard timeout / tab change / app deactivation, scrub in `closeEvent`; optionally a masked "reveal" output mirroring the passphrase Show/Hide.

#### L9. Forbidden-key / deny-list checks use exact, case-sensitive matching
*(Deduplicated: `audit-keys-case-substring-bypass` + `log-filter-no-recursion`.)*
- **File:** `src/gpg_meister/storage/audit_log.py:61-77, 116-127`; `src/gpg_meister/storage/log_config.py:24-40, 74-85`
- **What & attack scenario:** `FORBIDDEN_KEYS`/`_DENY_LIST` are matched with exact `in` equality, so near-miss key names (`master_passphrase`, `Passphrase`, `priv_key`) bypass redaction — notably `master_passphrase` is the codebase's established parameter name. Additionally, the diagnostic `sensitive_data_filter` only inspects top-level keys (the audit filter recurses), so a secret nested one level deep would be logged verbatim. **No current caller actually passes such a key, and no production code emits diagnostic logs**, so both are latent defense-in-depth gaps in deny-lists whose whole purpose is to survive future developer mistakes.
- **Fix:** Lowercase + substring-token match (`any(tok in key.lower() ...)`); make `sensitive_data_filter` recurse like `_check_payload_keys` and apply the `_CONTENT_TRIGGERS` PGP-header scan at every depth; unify both deny-lists in one shared module; add regression tests for `Passphrase`/`master_passphrase`/`priv_key` and a nested PGP block.

#### L10. Factory reset securely wipes only `gnupg/`; vaults, metadata DB, and logs use plain unlink
- **File:** `src/gpg_meister/storage/factory_reset.py:29-85`
- **What & attack scenario:** `_secure_wipe_gnupg_keys` overwrites only `data_dir/gnupg`; `perform_pending_factory_reset` then `shutil.rmtree`s everything else. The metadata DB (labels, fingerprints, timestamps) and audit/diagnostic logs are recoverable plaintext. Vault files are AEAD ciphertext (lower exposure), and shred is best-effort on SSD/CoW anyway, so the asymmetry is misleading rather than a key-material leak.
- **Fix:** Extend overwrite to the metadata DB + `-wal`/`-shm` sidecars and logs, **or** honestly document that secure deletion is unachievable without full-disk encryption and rename the gnupg shred so it does not imply the rest is wiped.

#### L11. Audit write/fsync failures are silently swallowed
- **File:** `src/gpg_meister/storage/audit_log.py:201-214`
- **What & attack scenario:** On `OSError` during write/flush/fsync the record is logged to the (lower-trust) diagnostic logger and dropped. A local actor who induces write failures (fill the FS, set EDQUOT, revoke the fd) can make security events vanish; dropped records are not detectable as a chain gap. Documented availability tradeoff.
- **Fix:** Maintain an in-process dropped-record counter surfaced to the UI / next successful record; consider refusing the highest-severity privileged operation on repeated audit-write failure.

#### L12. `verify_chain` follows symlinks and proves only consistency, not authenticity
- **File:** `src/gpg_meister/storage/audit_log.py:261-302`
- **What & attack scenario:** Reads log and `.tip` via `Path.open`/`read_text` without `O_NOFOLLOW` (the write path *does* harden with `reject_symlink` + `O_NOFOLLOW`), so a swapped symlink redirects verification. Combined with M2, success means "internally consistent," not "authentic."
- **Fix:** Open both files with `O_NOFOLLOW` for verification (mirror `__init__`); document success as "consistent" until the chain is keyed.

#### L13. TOCTOU between binary hashing and execution; whitelisted binaries get no content pin
- **File:** `src/gpg_meister/startup/gpg_detector.py:203-310`
- **What & attack scenario:** `detect()` hashes/stats the binary, then it is executed later. `_assert_binary_not_swapped` pins only `st_dev`/`st_ino`, so an **in-place** rewrite of the same inode is not detected; whitelisted binaries set `trusted_sha256=None` (`app.py:233`), so they get no cross-run content pinning at all. Writability/parent-writability/root-ownership checks already exclude unprivileged attackers — only root (or the owner of an explicitly pinned binary) can exploit this, i.e. an actor who already controls the host.
- **Fix:** Persist and re-verify SHA-256 for whitelisted binaries too; document the residual window; ideally re-hash (or open-and-exec via held fd) immediately before first invocation.

#### L14. `reject_symlink` then non-`O_NOFOLLOW` open is a TOCTOU pair
- **File:** `src/gpg_meister/storage/metadata_store.py:70-87` (+ `audit_log.py:237,250`)
- **What & attack scenario:** `reject_symlink(path)` (lstat) precedes `sqlite3.connect` (follows symlinks; cannot take an fd). A swap in the window could redirect SQLite. The audit `_scan_for_last_hash` reads are read-only and lock-guarded (lower impact). The enforced `0700` parent is the real mitigation, so exploitation needs a pre-existing permission weakness.
- **Fix:** For the SQLite path, document the residual risk and rely on the `0700` parent (SQLite cannot accept an fd); for `_scan_for_last_hash`, open with `os.open(..., O_NOFOLLOW)` and wrap the fd.

## 3. Clean-Code & Refactoring

**GPG service (`services/gpg_service.py`)**
- `decode-replace-status` (126-127, 159-165, *info*): `_decode_output` uses `errors="replace"`, turning non-UTF-8 status bytes into U+FFFD before splitting. Benign for security fields (all ASCII), but parse status as bytes / split before decoding.
- `missing-dashdash-separator` (402-409, 434, 446, 630, *info*): positional args passed to `gpg` without a `--` end-of-options separator. Not reachable today (fingerprints/user-IDs/expiry are strictly validated, temp paths are app-generated) but cheap future-proofing — insert `--` before the first positional in each command list.

**Vault service (`services/vault_service.py`)**
- `redundant-manifest-reserialise` (285-301, *low*): manifest serialized twice; the second call only recomputes a known length and leaves an un-zeroed copy. Capture `manifest_len = len(manifest_bytes)` once.
- `missing-empty-payload-guard` (263, *low*): `payload[0]` on a 0-byte plaintext raises an unaudited `IndexError`. Add `if not payload: raise VaultFormatError(...)`.
- `local-import-in-hot-path` (266, 519, *info*): `import io` and `GPGPassphraseError` are function-local with no circular-import justification — move to the module top.

**Storage layer**
- `atomic-write-no-mode-on-existing` (`atomic_write.py:66-91`, *info*): `os.replace` discards a target's stricter pre-existing mode (e.g. 0400→0600) and the mode is umask-masked with no follow-up `fchmod`. `fchmod` the fd after `os.open` (as `log_config.py`/`audit_log.py` already do).
- `umask-not-threadsafe` (`metadata_store.py:74-84`, *low*): process-global `os.umask` juggling during construction is fragile; the explicit `_fchmod_nofollow` already covers the need — drop the umask dance.
- `factory-reset-marker-symlink-helper-misuse` (`factory_reset.py:60-67, 79-82`, *low*): `reject_symlink_tree` is called on a single marker file; use `reject_symlink`. The directory-deletion TOCTOU is well-mitigated by the `0700` parent + `rmtree` fd-relative traversal.

**App / startup**
- `broad-except-factory-reset` (`app.py:140-144`, *low*): blanket `except Exception` around `perform_pending_factory_reset` masks programming errors and runs *before* logging is configured. Catch `(OSError, RuntimeError)` and let unexpected errors propagate to a top-level handler.
- `no-timeout-on-version-stderr` (`environment_check.py:96-115`, *low*): `check_gpg_version` ignores `returncode` and parses stdout only. Check returncode, scan stdout+stderr, include a snippet in errors.

**UI**
- `vault-export-dup-method` (`vault_export_view.py:165-229`, *low*): `_on_keys_loaded` is defined twice (the first is dead code); `_refresh_item_text`/`_init_item_name` duplicate prefix logic and rely on fragile string slicing. Delete the dead definition and store the display name in `UserRole` data. (Note: the prefixes are single codepoints, so the slice is fragile-but-not-currently-broken.)

## 4. Best Practices 2026 (Python / Packaging / Tooling)

- **Make advertised quality gates real and CI-enforced.**
  - `ruff-not-clean` (*low*): 19 lint errors (6 unused imports incl. dead `VaultFormatError`/`VaultChecksumMismatchError` in `vault_import_view.py`, whitespace, unsorted imports, an en-dash in `config_service.py:45`, one `SIM117`). Run `ruff check --fix`, fix the en-dash, gate in CI. (The "early-return skips validation" / "missing error branch" sub-claims were false positives — the return is inside `if not p.exists():` and a checksum-mismatch path exists.)
  - `mypy-not-clean` (`pyproject.toml:75-90`, *low*): `mypy --strict` reports 51 errors (7 in `src`: `key_list_view.py:64` `setCurrentItem` overload, `vault_export_view.py`, `gpg_trust_dialog.py`, `help_view.py`). Fix the 7 `src` errors and gate in CI; either fix or separately scope the 44 test errors.
- **Supply-chain provenance.** `sbom-not-wired-to-build` (`scripts/generate_sbom.sh:9-14`, *low*): SBOM is generated from the dev `.venv` (includes ruff/mypy/pyinstaller), not the shipped closure, and no build script invokes it. Generate from the locked runtime closure, call it from each build script post-artifact, and add it to `sign_release.sh`'s signed `SHA256SUMS` set.
- **Single-source the version.** `version-duplicated` (`packaging/macos/setup.py:23-24` vs `pyproject.toml:3`, *low*): `1.0.3` is hard-coded in both `CFBundleShortVersionString`/`CFBundleVersion` and `pyproject`. Derive from `importlib.metadata.version()` or adopt `hatch-vcs`. (The manifests do *not* currently duplicate the string, contrary to the finding's aside.)
- **Build-spec hygiene.** `appimage-windows-spec` (`scripts/build_appimage.sh:15`, *low*): the Linux AppImage is built from `packaging/windows/gpg-meister.spec`. The spec is platform-generic today (no Windows-only options), so this is a maintainability/release-org hazard, not a current break. Move to a shared/`linux` spec and run the AppImage build in CI before tagging.
- **Installer portability.** `install-sh-debian-only` (`install.sh:7-22`, *low*): unconditional `sudo apt-get` with no OS detection (`set -euo pipefail` aborts mid-run on non-Debian after sudo). Detect the package manager or document Debian/Ubuntu-only and exit early.
- **Flatpak sandbox scope.** `flatpak-gnupg-rw-scope` (`io.github.arn-c0de.GPGMeister.yaml:13-15`, *low*): `--filesystem=~/.gnupg:ro` exposes all private keys at rest, though the app reads only public keys; the comment understates this. Scope narrower or use portal file-selection. Also bump the aging KDE `6.7` runtime (app needs PySide6 ≥ 6.11; Qt is pip-bundled so it likely still runs).
- **Password policy modernization.** `password-policy-weak-thresholds` (`security/password_policy.py:50-145`, *low*): ~25-entry hard-coded common list, character-class counting (no entropy/repeat/sequence detection), no per-word checks; the policy is advisory-only in the vault-export flow. ## 6. Verification Notes

Each finding was checked against the actual working-tree code at the audited HEAD `94e85cd` (branch context `1.0.3-fixes`), including reading the cited files/line ranges, tracing reachability through callers (viewmodels, message/vault services, UI views), running `ruff`/`mypy`, and empirically exercising CPython internals (the interned single-byte corruption in `_zero_bytes_object`, msgpack length-limit behavior). A recurring and important finding is **branch divergence**: commit `67c6be9` is *not* an ancestor of HEAD (`git merge-base --is-ancestor` negative), so several "already fixed" hardenings (env isolation, dedicated status-fd, NUL rejection) are absent from the audited code — the fixes exist but were never merged into the release line. Severities were adjusted downward from several original "high"/"medium" ratings where attack preconditions (local memory access, prior root, attacker-controlled environment) or existing caps (256 MiB ciphertext limit, returncode-based validity for `BADSIG`/`ERRSIG`) bounded real-world impact.

**Four findings were rejected as false positives** after verification:
1. *"Legacy reconstruction trusts attacker-controlled key lengths before re-packing"* — `bytes.fromhex` is unreachable with bad input because `VaultManifest.model_validate` (with a 40-char-hex field validator) runs before `_append_key_material`, and the block is exception-wrapped; it added nothing beyond the separate legacy-msgpack finding.
2. *"run_all_checks crashes on non-numeric/4-part versions"* — the regex captures exactly three integer groups via unanchored `re.search`, so `int()` cannot throw and suffixed/4-part versions parse cleanly; the finding's own body conceded the no-throw point.
3. *"_resolve_gpg pins a swapped binary during the approval window"* — `detect()` re-hashes and enforces `trusted_hash == sha` (`gpg_detector.py:250`), so only the user-approved hash can be persisted; the missing `return` is a clarity nit, not a TOCTOU.
4. *"Config loaded and trusted before permissions validated"* — `config_service.load()` calls `ensure_safe_to_load()` *before* reading/parsing, rejecting symlink/world-/group-writable configs and failing closed; the recommended fix is already implemented.
